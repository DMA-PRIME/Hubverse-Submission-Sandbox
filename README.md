# DMA-PRIME Hubverse Submission Sandbox

This public repository teaches the GitHub mechanics used for a Hubverse-style submission: fork a repository, create a branch, add files at exact paths, open a pull request, read automated checks, and correct the same branch.

It is a classroom sandbox—not an operational forecasting hub. Passing its checks does not submit anything to CDC, ECDC, a Scenario Modeling Hub, or another real hub.

## Public repository warning

Everything uploaded or committed here is publicly viewable and downloadable. Closed pull requests and deleted files may remain visible in Git history or in copies already downloaded by other people.

Use only the synthetic practice files generated by the companion submission guide. Never upload:

- real or operational forecasts;
- real model metadata;
- private, confidential, identifiable, embargoed, or restricted data;
- names, student numbers, email addresses, credentials, tokens, or secrets.

## How many students can practice at once

Each student works independently:

1. Create a personal fork of `DMA-PRIME/Hubverse-Submission-Sandbox`.
2. Create a new branch in that fork.
3. Add one uniquely named synthetic metadata/output pair.
4. Open a pull request from the personal fork and branch to this repository's `main` branch.
5. Correct failures by updating that same branch.
6. Leave the pull request open for instructor acknowledgment.
7. The instructor closes the practice pull request **without merging it**.

Because practice pull requests are not merged, many students can propose files simultaneously without accumulating class submissions on `main`. Pull requests remain public after closure, so synthetic files are still required.

## Student quick start

The companion guide generates a random public practice model ID such as `learner-a7k9m2` plus two matching synthetic files. Use the generated ID; do not replace it with your real name, student number, email address, or operational model ID.

The generated paths follow this pattern:

```text
model-metadata/<practice_model_id>.yml
model-output/<practice_model_id>/<practice_date>-<practice_model_id>.csv
```

Example:

```text
model-metadata/learner-a7k9m2.yml
model-output/learner-a7k9m2/2026-09-03-learner-a7k9m2.csv
```

See [CONTRIBUTING.md](CONTRIBUTING.md) for the complete repository workflow.

## What the teaching check validates

The validator checks the relationships that often confuse first-time contributors:

- the metadata and output use the same `<team_abbr>-<model_abbr>` practice ID;
- the metadata filename and contents agree;
- the model-output subfolder and filename agree;
- the output filename begins with a valid round ID;
- both a metadata file and an output file are included;
- CSV/TSV files use one of the two small teaching schemas;
- an ISO filename date agrees with `reference_date` or `origin_date` in the file;
- the pull request changes only `model-metadata/` and `model-output/` files.

The check intentionally does not reproduce any operational hub's full schema, target, timing, authorization, or acceptance rules.

## Supported synthetic teaching schemas

Forecast:

```text
reference_date,target,horizon,target_end_date,location,output_type,output_type_id,value
```

Scenario:

```text
origin_date,scenario_id,target,horizon,location,age_group,output_type,output_type_id,value,run_grouping,stochastic_run
```

The public practice package uses CSV so learners can inspect it easily. The validator can also recognize TSV and perform a limited file-signature check for Parquet, but that is not full Parquet validation.

## Practice completion

For this sandbox, completion means:

1. the required check is green;
2. an instructor acknowledges the result; and
3. the pull request is closed without merging.

Real hubs have their own acceptance and merge policies. Always return to the selected hub's current instructions before submitting real files.

## Maintainer note about workflow approval

GitHub may require a maintainer to approve a workflow run from a first-time contributor's public fork. Inspect the proposed files before approving the run. The workflow uses a read-only token and no secrets.
